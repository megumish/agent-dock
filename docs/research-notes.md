# 設計判断一覧の調査ノート

この文書は、[DESIGN.md](../DESIGN.md) の設計判断一覧にある設計点ごとに、調査時点の事実、候補、暫定評価を記録する。
記述の拘束力は、DESIGN の「記述の効力」に従う。

- **確認済み事実**：見出しの日付時点で、ローカル環境または記録済みの証拠から確認した内容を指す。
- **候補**：ADR で比較する対象を指し、列挙した案がすべてとは限らない。
- **暫定評価**：確認済み事実と DESIGN の制約から見た現時点の選好を指し、ADR を拘束しない。
- 外部の製品、ライブラリ、標準に関する記載は調査の手掛かりであり、現行の仕様を保証しない。
- ADR を起草するときは、環境、外部資料、候補の適合性を改めて確認する。
- 調査した範囲で候補を確認できなかった場合は、調査範囲と確認できなかった理由を記録する。

## D-01 実行基盤（2026-07-31）

- 確認済み事実：ローカル照合で、Claude Code `2.1.220` と Codex CLI `0.144.4` の導入を確認した。
- 確認済み事実：同じ照合で、Gemini CLI `0.47.0`、jj `0.43.0`、SQLite `3.51.0` の導入を確認した。
- 確認済み事実：ローカルの CLI ヘルプでは、Claude Code の `-p` と `--output-format json`、許可関連のオプション、フック機構を確認した。
- 確認済み事実：ローカルの CLI ヘルプでは、Codex CLI の `codex exec --json` を確認した。
- 確認済み事実：ローカルの CLI ヘルプでは、Gemini CLI の `-p` と `--output-format json` を確認した。
- 未確認事項：各 CLI を実行した結果に、総コストと所要時間がどの形式で含まれるかは再確認していない。
- 既存 CLI を束ねる候補：各 CLI のヘッドレス実行と JSON 出力を、共通の実行アダプタで扱う。
- 自前ハーネスの候補：Claude Agent SDK、各社の SDK、LiteLLM を比較対象にする。
- 暫定評価：既存 CLI を束ねる方式を主軸とし、共通契約を満たせない箇所だけ自前ハーネスで補う。
- 暫定評価の根拠：導入済み CLI でヘッドレス実行と機械可読な出力を確認できたため、実行基盤を作り直す前にアダプタの適合性を測れる。

## D-02 イベント封筒と保存先（2026-07-29）

- 参考候補：CloudEvents、OpenTelemetry のトレースとスパン、W3C Trace Context を封筒と因果参照の比較材料にする。
- ストレージ候補：SQLite、追記型の JSONL と派生インデックス、DuckDB を比較する。
- 確認済み事実：記載時点の環境では SQLite が導入済みであり、DuckDB は未導入だった。
- SQLite の検討事項：更新拒否をトリガーで補助する案があるが、追記だけを保証できるかは ADR の試験で確認する。
- 暫定評価：共通項目を持つ封筒へイベント型ごとの項目を追加し、イベント本体は参照とハッシュで扱う。
- 暫定評価：v0 ストアには SQLite または JSONL を使う。
- 暫定評価の根拠：どちらも Phase 0 で小さく始められ、最終ストアを決めずに封筒と追記処理を検証できる。

## D-03 タスク分類（2026-07-29）

- 再確認事項：ADR の起草時に、調査対象とした分類体系と適用条件を記録する。
- 暫定評価：`unclassified` と自由タグを Phase 1 の最小形とする。
- 追加候補：設計、実装、大量編集、調査、レビュー、運用の六分類を暫定語彙へ加える。
- 暫定評価の根拠：未分類値で記録を欠落させず、六分類の不足と重複を Phase 1 で観測できる。
- 運用条件：分類を改訂しても凍結済みの評価対象群は書き換えず、改訂後の分類を使う比較は新たに事前登録する。

## D-06 フィードバックの操作設計（2026-07-29）

- 明示フィードバックの候補：完了時の一操作または一文字入力と、`/rate` に相当するコマンドを比較する。
- 実装部品の候補：Claude Code のフック機構と、`gum` などの端末ユーザーインターフェース部品を比較する。
- 暫定評価：受動シグナルは自動記録し、明示フィードバックは監査対象と必要な場面へ絞る。
- 暫定評価：受動シグナルは観測または代理信号として扱い、教師信号の代用や現在のユーザー判定の上書きには使わない。
- 暫定評価：明示フィードバックを求める場合は、一操作以内を手間の上限候補とする。
- 暫定評価の根拠：明示入力をすべての実行へ要求すると、D-16 が定める手間の上限を超える可能性があるため、Phase 1 で応答率と手間を測る。

## D-07 リプレイ方式（2026-07-29）

- 制約：このリポジトリでは直接の Git コマンド操作を避けるため、Git のワークツリーを使う場合も jj と整合するアダプタを介する。
- 未調査事項：判定基準の候補と、再演予算の単位および上限は調査していない。
- 暫定評価：現時点では VCS の分離方式を選ばない。
- 暫定評価の根拠：jj のワークスペースと隔離コピーについて、再構成時間、隔離の確実性、後始末の手間を実測していない。

## D-12 代行評価の監査（2026-07-29）

- 暫定評価の根拠：初期の一致率を領域ごとの最小標本数まで測り、運用が安定した領域では最低監査率を保ちながらユーザーの手間を減らす必要がある。

## D-21 秘密、送信、保持境界の執行（2026-07-29）

- 補助防御の候補：秘密パターン検査には、`gitleaks` と `trufflehog` のルールを比較する。

- 暫定評価：外部送信先の許可リスト、ツール実行の仲介、方針スナップショットを併用する。

- 暫定評価の根拠：送信と実行の境界だけでは、Phase 0 で始める正典記録の保持期限や認可済み削除を執行できない。

## D-22 資格ライフサイクル（2026-07-29）

- 状態機械ライブラリの候補：`python-statemachine` と `XState` を比較する。
- 未確認事項：ライブラリの依存と表現力が、必要な状態遷移と監査記録に見合うかは確認していない。
- 暫定評価：資格状態の変更を遷移イベントとして正典記録へ追加する。
- 暫定評価：資格の付与と再付与にはユーザーの承認を必須とする。
- 暫定評価の根拠：宣言した遷移と実際の承認を別々に記録すると、資格の根拠と変更主体を再構成できる。

## D-23 監査再構成契約（2026-07-29）

- 未調査事項：監査再構成契約を提供する既存 OSS について、調査範囲と不適合理由を記録していないため、有無を結論づけない。
- 参考候補：イベントソーシングの監査パターンを、来歴を保存する設計の比較材料にする。
- 暫定評価：決定イベントには、候補集合、棄却理由、適用した方針と上書きの版、証拠スナップショットと射影の来歴への参照を記録する。
- 暫定評価：監査用スナップショットへ削除対象を複製せず、削除された参照は理由を添えて利用不能と表示する。
- 暫定評価の根拠：現在の可変な状態だけを参照すると、決定時点の候補と根拠を後から再構成できない。

## D-24 障害時のイベント完全性（2026-07-29）

- **outbox パターン**：実行前の意図と配送対象を永続化し、未配送の処理を後から検出できるようにする設計を指す。
- 参考候補：イベント配送には、メッセージキューで使われる配送方式と、分散システムの outbox パターンを比較材料にする。
- 未確認事項：メッセージキュー製品の導入が、ローカルの単一利用者という前提に見合うかは確認していない。
- 暫定評価：イベント配送では、少なくとも一回の配送、重複検出、outbox パターンを参考にした永続化を組み合わせる。
- 暫定評価：実行指示では、冪等性キー、永続的な重複防止、レシートの突き合わせを候補とする。
- 暫定評価の根拠：イベント配送の重複は検出と突き合わせで処理できるが、非冪等または不可逆な操作の重複は作用前に防ぐ必要がある。
